# VaultKeeper — Independent Test & Fact-Check Report

**Repository:** `https://github.com/esskslifetech/VaultKeeper` (branch `main`, HEAD `9ea1fc1`)
**Reviewed:** 2026-09-20
**Toolchain:** Foundry `forge/cast/anvil 1.8.3`, solc 0.8.28 (`via_ir = true`), Node v20.20.2, Linux x86-64
**Method:** cloned the repo, compiled it, ran its own CI steps, ran its own tests, wrote **26 new independent tests** against the source, deployed to a local Anvil node, and fact-checked every external claim against the live web.

---

## 1. Verdict

**The repository does not do what it says it does.** The Solidity compiles, and two of its four tests pass — that is the extent of the working software.

| Question | Answer |
|---|---|
| Does it build? | ✅ `forge build` succeeds |
| Does it pass its own CI? | ❌ 2 of 4 CI steps fail (`forge fmt --check`, `forge test`) |
| Does its own test suite pass? | ❌ 3 passed / 1 failed |
| Do the deploy scripts run? | ❌ 4 of 5 fail; the README's documented command references a file that doesn't exist |
| Is the advertised frontend present? | ❌ `web/` is a dangling gitlink with no `.gitmodules` URL — **unrecoverable** |
| Is it an ERC-4626 vault? | ❌ 7 of 10 mandatory members are absent |
| Does the advertised end-to-end flow work? | ❌ It cannot: deposits never allocate, and the keeper cannot call the vault |
| README accuracy | ~40% of specific technical claims are false or unverifiable |

There is also strong, converging evidence the codebase was **AI-generated and never executed end-to-end**: the "Chainlink" dependency is a hand-written 2-file stub labelled as such, "proof" contracts return empty placeholder state with the comment *"This would normally query the vault keeper"*, the `vaultkeeper` CLI references paths that do not exist, and the type-annotated doc comments describe behaviour the code does not implement.

## 4. Findings

### CRITICAL

#### C-1. It is not an ERC-4626 vault
README: *"ERC-4626 compliant vault"* / repo description: *"ERC-4626 vault"*.

Empirically probed for each mandatory member (`test_A1`):

| Mandatory ERC-4626 member | Present? |
|---|---|
| `asset()` | ❌ |
| `mint(uint256,address)` | ❌ |
| `redeem(uint256,address,address)` | ❌ |
| `maxMint(address)` | ❌ |
| `previewMint(uint256)` | ❌ |
| `previewRedeem(uint256)` | ❌ |
| `withdraw(uint256,address,address)` | ❌ (the vault has `withdraw(uint256,address,uint256)` — different selector) |
| `totalAssets()` | ✅ |

Additionally:
- `maxWithdraw(owner)` returns `balanceOf(owner)` — a **share count**, where the spec requires **assets**. Verified skewed: reports `1000000000` when the true redeemable value is `200000000001000000000` (`test_A2`).
- `maxDeposit()` returns `type(uint256).max` **while paused**, i.e. it advertises a deposit that is guaranteed to revert (`test_A3`).
- `previewWithdraw()` rounds **down**; ERC-4626 requires rounding **up** (in favour of the vault).
- No virtual shares / decimals offset (see C-3).

#### C-2. Decimal mismatch corrupts NAV and locks user funds
`VaultKeeper._valueInDepositAsset()` converts a position to the deposit asset using **the oracle's decimals, not the token's**:

```solidity
function _valueInDepositAsset(address asset, uint256 amount) internal view returns (uint256) {
    uint256 price = priceFeed.getPrice(asset);
    uint8 decimals = priceFeed.decimals();      // <-- oracle decimals, not token decimals
    return (amount * price) / (10 ** decimals);
}
```

`totalAssets()` then **adds that result to `depositAsset.balanceOf(...)`**. With the exact configuration the repo deploys itself (`DeployLocalVaultKeeper.s.sol` creates USDC with **6** decimals and the stocks with **18**), 6-decimal units are summed with 18-decimal units.

Measured (`test_A4`) — 1,000 USDC deposited, then 1 AAPL.x worth $200 held by the vault:

```
reported totalAssets : 200000000001000000000
true USD value (6dp) : 1200000000
overstatement factor : 166,666,666,667  (1.67e11x)
```

The depositor then **cannot withdraw anything**:

```
shares held                 : 1000000000
assets it claims to be worth: 200000000001000000000
USDC actually in vault      : 1000000000
-> withdraw() reverts: InsufficientBalance
```

The consequence is that as soon as the vault holds any correctly-priced 18-decimal stock, share price explodes past every real balance and **the entire pool becomes unwithdrawable**. This is not a corner case; it is the default deployment.

#### C-3. Donation / share-inflation attack steals deposits
With no virtual shares or decimals offset, an attacker can make a victim's deposit mint **zero** shares (`test_A5`):

```
attacker: deposit(1 wei)      -> 1 share
attacker: transfer 500,000 USDC directly to the vault (donation)
victim:   deposit(1,000 USDC) -> 0 shares minted
=> deposit value is captured by the attacker
```

#### C-4. Slippage protection is hard-coded to zero
README: *"Slippage Protection via Uniswap V3 minimum output"*.

```solidity
function _sellAsset(address asset, uint256 valueInDepositAsset) internal {
    _swap(asset, address(depositAsset), amountIn, 0);   // <- minOut = 0
}
function _buyAsset(address asset, uint256 valueInDepositAsset) internal {
    _swap(address(depositAsset), asset, amountIn, 0);   // <- minOut = 0
}
```

Measured **on the wire** against a mock router that records the parameter (`test_B2`):

```
amountOutMinimum passed to router: 0
NAV before: 3,000,000,000,000,000,000,000,000   ($3M)
NAV after : 300,000,000                          ($0.0000003)
```

A fill that returns 1e-12 of value for a $2M position is accepted without complaint. The vault lost >99.99% of its value in a single rebalance.

#### C-5. Rebalancing liquidates the entire position instead of the excess
`_sellAsset` ignores the `excessValue` it is handed and sells the **whole balance**:

```solidity
function _sellAsset(address asset, uint256 valueInDepositAsset) internal {   // param unused
    uint256 amountIn = IERC20(asset).balanceOf(address(this));  // <-- sells everything
    ...
    _swap(asset, address(depositAsset), amountIn, 0);
}
```

Measured (`test_B1`) — target 50% AAPL, actual ~67%:

```
AAPL balance before : 10,000e18   ($2,000,000)
target weight (bps) : 5000
AAPL balance after  : 0           <-- should be ~7,500e18
USD  balance after  : 1,500,000e18
=> sells 100% of the position when only ~50% needed trimming
```

Since `rebalance()` then loops to the next underweight asset, it immediately stops selling the first and recycles capital — in the same run it also buys the second asset with **all** the cash, ending at roughly 0%/100% instead of 50%/50%. `moved++` is also incremented even when `_sellAsset`/`_buyAsset` return early without swapping.

#### C-6. Fees accrue off-book, then haircut holders at collection
`_assessFees()` adds to `_pendingFees[...]` but **never reduces `totalAssets()`**, so accrued fees stay inside NAV and inflate the share price. When `collectFees()` finally transfers them out, every holder takes a pro-rata loss.

Measured (`test_B4`) with the protocol-maximum fees (10% mgmt / 20% perf), 1 year elapsed:

```
NAV before fee assessment    : 1,000,000e18
NAV after  fee assessment    :   999,999.99999999995e18   <- flat (liability invisible)
share price before assessment: 1.000000000000000000e18
share price after  assessment: 0.999999999999999950e18    <- flat

fees wired to owner          : 299,999,800,000,000,000,000,000   (~30% of NAV)
share price before collect   : 3.000000000000000000e18  (after a top-up)
share price after  collect   : 2.700000000000000019e18  -> -10% haircut
```

Note also that with no public getter and a one-shot `collectFees()`, a holder cannot even observe the pending liability.

### HIGH

#### H-1. The keeper can never rebalance the vault, then bricks itself permanently
Nothing in any deploy script calls `vault.setKeeper(automation)`, so `Automation._executeRebalance()` → `vault.rebalance()` always reverts with `Unauthorized(caller, "KEEPER")` — which the `try/catch` converts into a silent failure counter.

```
consecutiveFailures: 3
lastError          : PERFORM_UPKEEP: 4e6f20616374696f6e20737563636565646564  ("No action succeeded")
totalRebalances    : 0
```

On the 4th attempt the circuit breaker becomes a **permanent lockout**:

```solidity
if (consecutiveFailures >= maxConsecutiveFailures) {
    revert ConsecutiveFailuresExceeded(consecutiveFailures, maxConsecutiveFailures);
}
```

`consecutiveFailures` is only reset on success — and success is now impossible, because the function reverts before doing anything. **There is no `resetConsecutiveFailures()`.** Once tripped, Chainlink Automation can never call this contract again. This directly refutes the README's *"no manual intervention required"*: intervention is required within the first three upkeeps.

Verified positively too (`test_C3`): after `vault.setKeeper(address(automation))` the upkeep succeeds. The defect is purely the missing wiring — plus the one-way lockout.

#### H-2. `strategyBreakdown().actualWeight` is not a weight
```solidity
uint256 actualWeight = total == 0 ? 0 : (balance * BPS_DENOMINATOR) / total;
```
It divides a **raw token count** by a **USD value**. For a portfolio sitting exactly on a 50/50 target (`test_B3`):

```
reported actualWeight AAPL: 12
reported actualWeight MSFT: 8
true weight should be     : 5000 / 5000
```

This broken metric feeds `Automation._checkPriceDeviation()`, which is why upkeep is requested **immediately on a brand-new empty vault** (`test_C1`):

```
upkeep needed immediately after deploy: true
bitmask before interval elapses: 2   (PRICE_DEVIATION)
```

A deployed keeper would rebalance every single block — burning gas on an empty vault — for as long as it survives H-1's lockout.

#### H-3. One upkeep executes `rebalance()` twice
`checkUpkeep` sets bit 0 for both `HEALTH_FACTOR` and `TIME_REBALANCE` (the code comment admits: *"using same bit for simplicity"*), and bit 1 for `PRICE_DEVIATION`. `performUpkeep` then calls `_executeRebalance()` for **each** bit:

```
trigger bitmask: 3
rebalances executed in ONE upkeep: 2
```

Two full rebalances per upkeep, the second computed from stale weights, at roughly double the gas.

#### H-4. "Cryptographic proof system" produces empty proofs
`RebalanceProof._getCurrentState()` is a stub with a literal admission in the source:

```solidity
function _getCurrentState() internal view returns (StrategyState memory) {
    // This would normally query the vault keeper for current state
    // For now, return empty state (to be populated by vault integration)
    return StrategyState({ assets: new address[](0), balances: new uint256[](0), ... });
}
```

And `snapshotPreRebalance()` fabricates its state root:

```solidity
stateRoot = keccak256(abi.encodePacked(block.timestamp, snapshotId));   // not a state root
```

Measured (`test_D1`, `test_D2`):

```
snapshot: assets 0, balances 0, totalValue 0
returned stateRoot == keccak256(abi.encodePacked(block.timestamp, id)) : true
generated proof: preState assets 0, postState assets 0,
                 totalValueBefore 0, totalValueAfter 0,
                 valueDelta 0, signature length 0
```

`RebalanceProof.sol` has **no reference to the vault at all** — no address, no interface, no call. `verifyRebalanceProof()` validates caller-supplied calldata against caller-supplied calldata, so "verification" is trivially forgeable. `txHash: blockhash(block.number - 1)` is a block hash, not a transaction hash. There is nothing cryptographic here and nothing verifiable.

#### H-5. The "weighted median" never sorts
`_aggregatePrice()` walks sources in **insertion order** accumulating weight and returns the first price whose cumulative weight exceeds half:

```solidity
uint256 targetWeight = totalWeight / 2;
for (uint i = 0; i < validCount; i++) {
    cumulative += weights[i];
    if (cumulative > targetWeight) { medianPrice = prices[i]; break; }
}
```

No sorting. For three equal-weight sources reporting 300 / 100 / 200, the returned "median" is **100** — the true median is 200 (`test_P2`). Reversing insertion order still returns position 2, i.e. the result depends on configuration order, not on prices (`test_P3`). An oracle whose output is controlled by the order in which sources were added is not an oracle.

#### H-6. `updatePrices()` is a total no-op for every caller
```solidity
function updatePrices(address[] calldata assets) external {
    _onlyOracleManager();
    for (...) { try this.updatePrice(assets[i]) {} catch {} }
}
```
`this.updatePrice(...)` is an **external** call, so `msg.sender` inside becomes the `PriceFeed` contract itself, which fails its own `_onlyOracleManager()` check — and the failure is swallowed by `catch {}`. Verified: **neither** asset is updated, and no error is surfaced (`test_P8`).

#### H-7. PriceFeed governance is frozen forever
```solidity
address public immutable owner;   // <-- immutable
...
function acceptOwnership() external {
    if (msg.sender != pendingOwner) revert Unauthorized(msg.sender, "PENDING_OWNER");
    emit OwnershipTransferred(owner, pendingOwner);
    pendingOwner = address(0);    // <-- owner is never assigned
}
```
Measured (`test_P6`): after `transferOwnership(bee)` + `acceptOwnership()`, `owner()` is unchanged and `pendingOwner` is zeroed. Because `owner` is `immutable`, **no code path can ever change it**. The advertised *"Two-step governance (pending governor)"* is dead code. (`oracleManager` is mutable, so the feed is not bricked — but `_onlyOwner()` is unreachable forever.)

#### H-8. The PriceFeed "circuit breaker" can never engage
`updatePrice()` writes `lastCircuitBreakerTrigger = block.timestamp` and then **reverts in the same transaction** — which rolls the write back:

```
lastCircuitBreakerTrigger after trip: 0
another asset updates immediately despite the "active" breaker: ok
```

Verified (`test_P7`). The breaker is a plain revert with no persisting state.

## 6. What genuinely works

Being fair to the project — these parts are real and correct:

1. **It compiles cleanly** under solc 0.8.28 with `via_ir`, and all contracts are well under the EIP-170 size limit.
2. **Access control is sound**: unauthorised `rebalance()` reverts with `Unauthorized(caller,"KEEPER")`; fee setters enforce their maxima; `_validateStrategy` correctly enforces length, `MAX_STRATEGIES` (8), `MAX_SINGLE_WEIGHT` (9000 bps) and weight-sum = 10,000. Verified in `test_B5`.

4. **Chainlink price aggregation and decimal normalisation are correct**: an 8-dp feed into an 8-dp PriceFeed passes through; an 18-dp feed is down-scaled; an 8-dp feed is up-scaled into an 18-dp PriceFeed. Verified in `test_P1`.
5. **Staleness protection works**, including the 300-second heartbeat grace (`test_P4`).
6. **`DeployLocalVaultKeeper.s.sol` deploys successfully** to Anvil — the one working script.
7. **The Uniswap V3 interface is accurately transcribed** and the default router address is the real mainnet SwapRouter.
8. **The Pyth and forge-std/OpenZeppelin vendored code is genuine**, not stubbed.
9. The README's dependency versions all correspond to real published packages.
10. The **USD-affecting mitigations are well-intentioned**: custom errors instead of revert strings, HWM-based performance fees, per-asset staleness overrides, source health auto-disabling after 3 consecutive failures, two-step governance *intent*.

## 8. Bottom line

The gap here is not a list of bugs; it is that the **product described in the README does not exist**. Of the five contracts the README advertises as the value proposition, three are non-functional placeholders:

- the vault is not ERC-4626 and mangles its own NAV,
- the "keeper" cannot call the vault and permanently disables itself,
- the "cryptographic proof system" holds no state and signs nothing,
- the "multi-oracle aggregator" is not a median and its governance is frozen,
- the frontend, API layer and subgraph are absent entirely.

For anyone evaluating this as a hackathon entry or a portfolio piece, the honest characterisation is: **an impressively structured scaffold with a very thorough README, where the scaffolding — not the functionality — was built.** Nothing here should be deployed, and no claim in the README should be relied upon without re-verification.

Should you want to salvage it, the highest-value order of work is: fix the decimal handling in `_valueInDepositAsset`/`totalAssets` (C-2) → add virtual shares/decimals offset (C-3) → pass real `minOut` and sell only the excess (C-4/C-5) → make fees reduce NAV as they accrue (C-6) → wire `setKeeper` and make the circuit breaker resettable (H-1) → then replace the stub contracts (`RebalanceProof`, the Chainlink stub) or delete them and cut the corresponding README claims.
